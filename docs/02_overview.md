What user will give to optimizer
1. details
- origin
- dest
- Cargo:
    - commodity
    - size (in cubic meters or tons idk)
- laycan start
- laycan end
- planning_horizon_days
- Vessels:
    - vessel_id
    - class (handy/supra/pana/cape)
    - current_location (port or at sea)
    - status (idle, on TC, on voyage)
    - available_from (date)
    - available_until (date)
    - fuel_capacity
    - fuel_consumption_rate
    - speed
- TC hire quotes (today's real-world $/day quotes for each vessel class, not forecasts)
2. hyperparameters
- risk_tolerance (how much to weigh expected cost vs variance)
- penalty for idle days
- penalty for ballast days
- penalty for late delivery
- etc. etc.

What optimizer gets from ML model (or some other forecast source (including a table produced by an ML model))
- price forecasts in TCE quantiles for each route × vessel class × future date within planning horizon
    - so nothing about your ship, fuel bill, or schedule goes into the ML model
- fan_width: volatility bands for each route × vessel class × future date

What optimizer gets from static reference
- port_specs:
    - per-berth max LOA, beam, draft, dwt, handling rate, handling capacity
- port distance matrix (for voyage time calculation)
- speed-fuel-consumption curves (per vessel class)
- port dues
- bunker prices (per port, per fuel grade)
- expected_wait_days (per port, per vessel class, per day) — from PortWatch/AIS or other source

What user gets from optimizer (after the optimizer gets what it wants):
1. Lock/wait + ceiling: "Sign a 6-month Supramax TC now if you find ≤ $18,500/day; walk away above that." (Ceiling = the fixed rate that still beats the spot fan across 6 months.)
2. Voyage schedule: "Vessel A loads parcel #3 at Kalimantan May 12, discharges Paradip May 26, then heads to Richards Bay for parcel #4."
3. Repositioning: "Don't idle at Paradip after #3 — queue's 4 days and no next cargo till June; sail empty toward Singapore (P(cargo within 10d) ≈ 70%)."
4. Savings, as a range: "+$2,100/day expected vs always-spot; even in bad runs +$800 (P10)."
5. Review date: "Re-solve weekly, or immediately if BDI jumps >5%."

---

What the ML model needs to be trained (so that it can provide the optimizer what it wants):
- the target grid is route x vessel_class x future_date (TCE in usd/day)
- free reality: we have DENSE history for class x date (decades), SPARSE for named routes (weekly anchors)
    - nobody sells the full cube; so decompose instead of collecting our way out

data collected -> what it becomes
- investing.com csv backfill (BDI + BCI/BPI/BSI/BHSI): daily class TCE averages, decades deep -> layer 1 base series + volatility features
- handybulk daily/monthly archives: same indices PLUS per-class average TC earnings in $/day (2016+, archivable) -> layer 1 cross-validation + the actual $/day units the optimizer wants
    - note: bci index points != usd/day tc average; two different series, collect both columns
- signal group weekly monitors on HSN (incl "Indonesia Thermal Coal to India" series): ~12 named routes (C5, P5_82, S10, C3...) at weekly cadence + Indian Ocean ballaster counts -> layer 2 anchors + supply-side features
- reference/baltic_routes.csv: static dictionary (route_code -> class, load/discharge ranges, unit, weighting) -> join table, not training rows

construction: TCE(route r, class c, t+h) = BASE(c, t+h) x (1 + BASIS(r))
- ML owns the BASE only: pooled model over classes at grain (class x date), trained on dense history
    - physics stays OUT of the model: distance, transit time, fuel, port costs are the optimizer's own voyage estimation
- BASIS is a calibration TABLE, not a model:
    route_family     basis_mean   basis_std   n_anchors   source
    indo_ec_india    -8%          6%          ~20         signal weekly anchors
    pacific_rv       0%           3%          ~40         signal weekly anchors
    synthetic_*      0%           12%         0           prior
    - basis captures market effects physics cannot see (e.g. ballast tonnage parked in Indian Ocean discounting India-bound routes)
    - optimizer applies quantiles x (1 + basis_mean) and widens fan_width by basis_std
    - regenerated by a dumb stats script whenever anchor archive grows; promote to a learned spread model ONLY if basis turns out predictable, not just measurable
- route survives as a join key for per-route congestion features (origin/dest port calls via ports_index mapping)

long-format master table (one row per observation)
    series_id | date | value | unit
    C5TC      | 2019-03-04 | 14250 | usd/day     <- class base series
    S8_TCE    | 2024-06-11 | 17800 | usd/day     <- route anchor (feeds BASIS table)
- features/targets are GENERATED by lagging/shifting, never hand-built:
    sample = (class=Supramax, date t)                  <- built: data/samples_{train,valid,test}.parquet
    features: TCavg lags t..t-63, rolling vol/z-scores, calendar (CNY, monsoon, fiscal qtr), congestion counts...
    targets:  y_step_h7, y_step_h30, y_step_h90 (log $/day), one pooled model per horizon
    verified: embargo gaps ~5 months between splits, targets bit-exact vs shifted source except at data gaps
- iron rule: features at row t may only contain info published <= t
    train/test split chronological with embargo gap >= longest lookback + horizon (e.g. 60 trading days)
    walk-forward cv, never k-fold shuffle
- output contract back to optimizer: per (class, horizon): P10/P50/P90 of base TCE -> point = P50, fan = P90-P10
    - per-route values are derived optimizer-side: quantiles x (1 + BASIS(r)), fan widened by BASIS(r).basis_std
